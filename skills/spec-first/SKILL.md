# Spec first

仕様は短い。1 画面に収まらない仕様は、作業を分割する合図。

## 仕様に書くもの（この順、この見出し）

1. **目的。** 誰の何が変わるか。1 文。続けて `満たす: R-xx, R-yy`。`docs/REQUIREMENTS.md` の不変条件の ID を書く。どれにも当たらなければ `満たす: なし（R-xx 追加候補）` と書く。利用者（エンドユーザー、ライブラリの呼び出し側）と、このコードを次に保守する人の両方について書く。
2. **完了条件。** 箇条書き。各項目は「実行すれば真偽が分かる文」にする。判定方法を括弧で添える。
   - 良い例: 「`POST /export` を同じ idempotency-key で 2 回呼ぶと、2 回目は 200 で行数が増えない（`scripts/verify-export.ts` で確認）」
   - 悪い例: 「エクスポートが安定する」。判定できないので、何を観測すれば安定と言えるかを書き直す。
3. **データの形。** 入力と出力と状態の型。TypeScript の型定義をそのまま書く。principle-model-the-domain に従い、散らばった条件分岐ではなく、状態機械・テーブル・判別可能なユニオンのどれで表すかを決める。
4. **非目標。** やらないことを 3 つまで。スコープの膨張を防ぐ。
5. **検証方法。** 完了条件を自動で確かめるスクリプトまたはテストの置き場所。principle-prove-it-works に従い、レビュアーが再実行できる形にする。まだ無ければ「作る」と書き、Feature の最初の単位にする。

## 手順

1. `docs/REQUIREMENTS.md` があれば「不変条件」と「非目標」を読む。非目標に当たる依頼は書かずに報告する。
2. `docs/specs/` を見る。同じ slug があれば更新モード。差分だけ直す。
3. 依頼文から上の 5 項目を埋める。埋まらない項目は、空欄にせず「未定: 理由」と書く。
4. 完了条件のうち、実験で決まるもの（挙動、性能、レイアウト）は poteto-mode の Prototype プレイブックで決める。ユーザーに聞かない。
5. ユーザーにしか決められない項目（製品判断、優先順位）だけを「未決」として返答に書く。既定値を置いて作業は続ける。
6. 仕様をコミットする。仕様と実装は同じ PR に入れる。仕様だけの PR は作らない（最良の仕様はコード、という土台の思想に合わせる）。
7. 実装が仕様と食い違ったら、先に仕様を直す。返答で「仕様の変更点」を 1 行ずつ報告する。

## 書式

- 日本語。文章は unslop-ja に従う。
- 型定義とコマンドはコードブロック。
- 1 画面（60 行程度）を超えたら、仕様を分割するか、非目標を増やす。

## テンプレート

```markdown
# <機能名>

## 目的
<誰の何が変わるか。1 文。>
満たす: R-xx

## 完了条件
- [ ] <判定できる文>（<判定方法>）
- [ ] <判定できる文>（<判定方法>）

## データの形
```ts
// 入力、出力、状態
```
表し方: <状態機械 / テーブル / 判別可能なユニオン / その他> 理由: <1 文>

## 非目標
- <やらないこと>

## 検証方法
<スクリプトまたはテストのパス。無ければ「作る」>
```
